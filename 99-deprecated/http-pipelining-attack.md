# HTTP Pipelining & Connection Reuse Attack Mutation Taxonomy

---

## Classification Structure

HTTP/1.1 persistent connections (keep-alive) allow multiple request-response pairs over a single TCP/TLS socket. **HTTP pipelining** extends this by permitting clients to send multiple requests without waiting for intermediate responses, relying on the server to return responses in strict **FIFO order**. This mechanism — concatenating logically independent transactions onto a shared, ordered byte stream — creates an attack surface that is distinct from, though often enabled by, HTTP Request Smuggling (HRS).

**Scope distinction**: HRS (CL.TE, TE.CL, CL.0, etc.) is the mechanism for *injecting* extra requests into a pipeline. This taxonomy covers what happens **after injection** — the attacks that exploit the pipeline's structural properties. HRS primitives are summarized in Appendix A as pipeline injection enablers, not repeated here as a primary category.

### Three Classification Axes

- **Axis 1 — Pipeline Property Attacked** (what structural property of the pipeline is exploited): response ordering, connection state, response-request association, connection pool management, timing/sequencing, protocol boundary. This is the **primary** axis.
- **Axis 2 — Exploitation Mechanism** (how the property is violated): queue shift, state carry-over, boundary confusion, pool corruption, timing manipulation, amplification. This is the **cross-cutting** axis.
- **Axis 3 — Impact Scenario** (what the attacker achieves): session hijacking, credential theft, cache poisoning, ACL bypass, cross-origin data theft, DoS. This is the **mapping** axis.

### The Pipeline Contract

The HTTP/1.1 pipeline rests on three implicit contracts:

| Contract | Assumption | Attack When Violated |
|----------|-----------|---------------------|
| **FIFO ordering** | The Nth response corresponds to the Nth request | Response queue poisoning (§1) |
| **Request isolation** | Each request on a connection is independent; processing one does not affect another | Connection state attacks (§3) |
| **Connection integrity** | A connection carries traffic for one client; the byte stream is not shared across trust boundaries | Client-side pipeline poisoning (§4), Response smuggling (§2) |

Every attack in this taxonomy violates one or more of these contracts.

## §1. Response Queue Poisoning (RQP)

**The** quintessential pipeline attack. RQP exploits the FIFO contract: when an extra request is injected into the pipeline, the response queue shifts by one position, causing every subsequent user to receive someone else's response.

### §1-1. Simple Queue Shift (+1 Desync)

The attacker injects one extra request via any smuggling primitive (Appendix A). The back-end generates one extra response. Since the front-end expects responses in FIFO order matched to its own request count, every subsequent response is delivered to the wrong user.

| Subtype | Mechanism | Key Condition |
|---------|-----------|---------------|
| **Single-injection RQP** | One smuggled request creates a +1 response offset. The attacker receives the response to their smuggled request; the next user receives the response intended for the attacker's second request; cascade continues | Shared persistent connection between proxy and origin carrying multiple users' traffic |
| **Self-targeted RQP** | Attacker pipelines their own legitimate request immediately after the smuggled one to capture a specific victim's response | Attacker can control timing of requests on the shared connection |

**Attack flow:**
```
Normal pipeline (3 users sharing connection):
  User_A Req → Resp_A to User_A
  User_B Req → Resp_B to User_B
  User_C Req → Resp_C to User_C

After attacker injects Req_X via smuggling:
  Attacker Req  → Resp_Attacker to Attacker     (legitimate)
  Req_X (hidden)→ Resp_X generated by back-end
  User_B Req    → Resp_X to User_B              ← WRONG (gets attacker's smuggled response)
  User_C Req    → Resp_B to User_C              ← WRONG (gets User_B's response)
  User_D Req    → Resp_C to User_D              ← WRONG (cascade continues)
```

The queue remains poisoned until the connection is closed or recycled, meaning **every user on that connection** receives misaligned responses.

### §1-2. Cascading / Multi-Injection RQP

| Subtype | Mechanism | Key Condition |
|---------|-----------|---------------|
| **N-request injection** | Smuggle N requests simultaneously; response queue shifts by N positions, amplifying data leakage | Smuggling primitive supports multi-request payloads |
| **Repeated injection** | Continuously smuggle requests to keep the queue permanently poisoned | Attacker can sustain request flow to the target |
| **Bidirectional cascade** | Injected requests themselves trigger redirects or additional server-side requests, further compounding the queue shift | Smuggled requests hit endpoints with side effects |

On high-traffic targets, cascading RQP can leak hundreds of responses per minute. On Netlify's CDN, this technique produced a continuous stream of responses from **every website on the platform**, including authentication tokens and private data.

### §1-3. Header-Injection Escalated RQP

A low-impact HTTP header injection vulnerability (CRLF injection in a response header) becomes **critical** when combined with the pipeline's FIFO property.

| Subtype | Mechanism | Key Condition |
|---------|-----------|---------------|
| **CRLF → RQP** | Inject `\r\n\r\n` within a response header to terminate the current response early. The back-end continues writing what it thinks is the same response, but the front-end treats it as the start of the next response — shifting the queue | Response header value controllable by attacker (e.g., via redirect URL, Set-Cookie reflection) |
| **Request-line injection → RQP** | URL-encoded CRLF in a path that gets reflected in a `Location` header creates the same response-split + queue-shift | Application reflects request path in response headers without sanitization |

**Example (header injection → RQP):**
```
GET /%20HTTP/1.1%0d%0aHost:%20x.net%0d%0aConnection:%20keep-alive%0d%0a%0d%0aGET%20/%20HTTP/1.1%0d%0aFoo:%20bar HTTP/1.1
Host: target.com
```

The response contains the injected CRLF sequences. The front-end sees two complete responses where only one was expected — the queue shifts.

This transforms a typically-low-severity header injection into full account takeover via pipeline response misrouting, with bounty-confirmed cases.

### §1-4. RQP Race Conditions

| Subtype | Mechanism | Key Condition |
|---------|-----------|---------------|
| **Low-traffic timing** | On low-traffic targets, there may be no other users on the poisoned connection to receive misaligned responses, making exploitation unreliable | Attacker must race against connection idle timeout |
| **Connection pool lottery** | On high-traffic targets with large connection pools, the attacker's poisoned connection must serve the target victim | Probability proportional to 1/(pool size) |
| **Brute-force capture** | Send many smuggled requests to statistically increase the chance of capturing target responses | Public GitLab RQP case captured vulnerability reports via high-volume request attempts |

## §2. Response Smuggling / Response Desync

While HRS manipulates *request* boundaries, response smuggling manipulates *response* boundaries on the pipeline — causing the front-end proxy to misparse where one response ends and the next begins.

### §2-1. Response Boundary Confusion

| Subtype | Mechanism | Key Condition |
|---------|-----------|---------------|
| **Response CL mismatch** | Back-end sends a response with Content-Length that doesn't match actual body size. Proxy reads too few bytes → leftover data becomes prefix of next response. Or reads too many → consumes part of next response | Back-end miscalculates or lies about response body length |
| **Response TE mismatch** | Back-end uses chunked Transfer-Encoding in response that the proxy fails to properly dechunk | Proxy doesn't implement response dechunking correctly |
| **Implicit response length confusion** | HEAD response declares Content-Length N but has no body. Proxy reads N bytes of the *next* response as the HEAD body | Proxy incorrectly applies CL to HEAD responses |
| **Interim response confusion** | 100 Continue or 1xx responses cause the proxy to advance its pipeline state prematurely | Proxy mishandles interim responses in pipeline context |

### §2-2. Response Concatenation

Injecting multiple complete responses into a single back-end "response slot" causes the proxy to concatenate them, overriding security headers.

| Subtype | Mechanism | Key Condition |
|---------|-----------|---------------|
| **CSP bypass via concatenation** | When the proxy concatenates two responses, the Content-Security-Policy header from the smuggled response's headers becomes part of the body — only the first response's CSP applies | Proxy treats concatenated responses as a single response body |
| **Security header stripping** | X-Frame-Options, X-XSS-Protection, and similar headers on the smuggled response are ignored because they're in the "body" of the concatenated response | Front-end only reads headers from the first response boundary |
| **Content-Type confusion** | The smuggled response's Content-Type is ignored; the browser interprets its body using the first response's Content-Type | Enables XSS by having HTML interpreted under a permissive Content-Type |

### §2-3. Stacked-Response Problem (Client-Side)

When exploiting client-side desync (§4) through a browser, a critical challenge arises: if the browser receives more response data than Content-Length promises, it **discards the connection** rather than queuing excess data.

| Evasion Technique | Mechanism | Precision Required |
|-------------------|-----------|-------------------|
| **Cache-buster timing** | Use unique `?cb=` parameters to trigger cache misses, creating ~500ms delays between responses that allow the browser to read exactly one response per fetch | Moderate — depends on network latency |
| **Fragmented chunk encoding** | Use `Transfer-Encoding: chunked` responses with predictable chunk sizes to precisely control byte boundaries | High — must match exact response sizes |
| **HEAD method trick** | Send a HEAD request that declares Content-Length N. The browser reads N bytes of the *next* (smuggled) response as the HEAD body | High — must know exact size of target response |
| **Random header padding** | Pad smuggled request with headers to make its response a predictable size | Moderate — iterative tuning |

## §3. Connection State Attacks

Attacks exploiting the **stateful nature** of persistent connections: when multiple requests share a connection, the processing of request N can affect the behavior/routing/authorization of request N+1.

### §3-1. First-Request Routing

Many proxies make routing and authorization decisions based on the **first request** on a connection and apply that decision to all subsequent pipelined requests.

| Subtype | Mechanism | Key Condition |
|---------|-----------|---------------|
| **Whitelist-on-first-request** | Proxy checks URL/Host against an allowlist only for the first request. Subsequent requests on the same connection bypass the check entirely | Proxy caches access decision per connection, not per request |
| **Virtual host pinning** | Back-end pool assigned based on first request's Host header. Subsequent requests with different Host headers are silently forwarded to the original pool | Proxy selects backend once per connection |
| **Backend affinity exploitation** | Load balancer pins connection to a specific backend server. Attacker's first request reaches a server with different content/config than intended | Sticky session per connection, not per request |

**Example (whitelist bypass):**
```http
GET /public-api HTTP/1.1
Host: allowed.example.com
Connection: keep-alive

GET /internal-admin HTTP/1.1
Host: internal.example.com
```

The proxy evaluates the first request against its allowlist (passes), establishes a backend connection, and blindly forwards the second request — which targets an internal host — over the same connection.

### §3-2. Authentication State Carry-Over

| Subtype | Mechanism | Key Condition |
|---------|-----------|---------------|
| **Connection-level auth** | First request authenticates (mTLS, IP-based auth). Authentication state is bound to the connection, not the request. Subsequent requests from different users inherit the auth context | Proxy multiplexes users onto authenticated backend connections |
| **Session pinning across users** | Proxy forwards requests from User A and User B over the same backend connection. Backend's session middleware associates both with User A's session | Backend uses connection-level session tracking |
| **Token carry-over** | X-Auth-Token or similar header from first request is cached by a middleware and applied to subsequent requests on the same connection | Stateful middleware on shared connections |

### §3-3. Connection-Locked Smuggling & Double-Desync

Some desync vulnerabilities only manifest on the **same connection** — the smuggled request doesn't affect other connections. This requires a two-stage "double-desync" to weaponize.

| Subtype | Mechanism | Key Condition |
|---------|-----------|---------------|
| **0.CL → CL.0 conversion** | Stage 1: Trigger 0.CL to desync the connection. Stage 2: Exploit the now-confused connection state to achieve CL.0, which can affect other users | Requires early-response gadget (§5-1) for Stage 1 |
| **Header-length probing** | The front-end appends headers (X-Forwarded-For, etc.) to forwarded requests. Attacker must discover the exact byte length of these injected headers to calculate correct offsets for Stage 2 | Iterative probing with `0cl-find-offset.py` |
| **Reflection-based offset discovery** | Smuggle a request to an endpoint that reflects the request back. The reflected content reveals the exact injected headers and their lengths | Endpoint that echoes request headers in response body |

**Double-desync sequence:**
```
Stage 1 (0.CL — deadlock broken by early-response gadget):
  POST /con HTTP/1.1           ← IIS reserved filename = early response
  Content-Length: 92            ← back-end sees this, front-end doesn't

  GET /z HTTP/1.1               ← this becomes "body" for back-end
  Content-Length: 180
  Foo: GET /y HTTP/1.1
  ???: ????                     ← front-end injected headers land here

Stage 2 (CL.0 — exploit the desync'd connection):
  POST /index.asp HTTP/1.1
  Content-Length: 201
  [smuggled payload]
```

## §4. Client-Side Pipeline Poisoning

Client-side desync (CSD) attacks target the **browser's own connection pool** rather than a server-side proxy's connection pool. The victim's browser is tricked into desyncing its connection to a vulnerable server.

### §4-1. Browser Connection Pool Architecture

Browsers maintain separate connection pools segmented by:

| Pool Dimension | Segmentation | Attack Implication |
|---------------|-------------|-------------------|
| **Credentials** | With-cookies pool vs. without-cookies pool | `credentials: 'include'` targets the authenticated pool, enabling post-auth attacks |
| **Origin** | Separate pool per origin (scheme + host + port) | Attacker must target the exact origin of the vulnerable server |
| **Connection limit** | Typically 6 connections per origin (HTTP/1.1) | Poisoned connection has 1/6 chance of serving next navigation |

### §4-2. CSD Attack Variants

| Subtype | Mechanism | Key Condition |
|---------|-----------|---------------|
| **Cross-origin CL.0 CSD** | Attacker's JavaScript sends `fetch('https://target/static', {method:'POST', body:'smuggled-prefix', mode:'no-cors', credentials:'include'})`. Server ignores body on static endpoint → body poisons connection → next browser navigation to target uses poisoned connection | Server endpoint ignores POST body (static files, redirects) |
| **Pause-based CSD** | JavaScript sends request headers promising a body, then pauses. Server times out (Apache: 60s, Varnish: 15s) and leaves connection open for reuse. Follow-up request is prepended with leftover data | Server timeout doesn't close the connection |
| **H2.0 browser CSD** | Browser negotiates HTTP/2, but server's HTTP/2 implementation drops body data during processing. The body bytes persist in the connection as a desync prefix | Server HTTP/2 implementation has body-handling bugs |
| **Redirect-based CSD** | Server responds with 301/302 without consuming POST body. Browser follows redirect but the connection retains the unconsumed body bytes | Server-level redirect before body consumption |

### §4-3. CSD Exploitation Chains

Once the browser's connection is poisoned, the attacker leverages it for:

| Chain | Mechanism | Impact |
|-------|-----------|--------|
| **Stored XSS via cache poisoning** | Poisoned connection serves attacker-controlled response that gets cached by the browser. Subsequent navigations load the cached malicious response | Persistent client-side compromise |
| **Credential capture** | Poisoned connection prefix includes `GET /api/user HTTP/1.1`. Browser's next authenticated request is overridden — response contains victim's profile/tokens | Account takeover |
| **Session fixation** | Smuggled prefix sets attacker-controlled session cookies via `Set-Cookie` in the misrouted response | Session hijacking |
| **Web VPN escape** | On Cisco ASA WebVPN / Pulse Secure, CSD poisons the VPN's browser session, allowing attacker to execute JavaScript in the VPN's origin context | Internal network access from external attacker |

**Cisco ASA WebVPN CSD (CVE-2022-20713):**
```http
GET /+webvpn+/ HTTP/1.1
Host: attacker-controlled.net
```
The VPN's Host-header redirect creates a CL.0 desync. Attacker's JavaScript poisons the browser's VPN connection pool. Subsequent VPN navigations load attacker-controlled content in the VPN origin.

## §5. Pipeline Timing & Sequencing Attacks

Attacks exploiting the temporal properties of pipelined connections — timeouts, ordering guarantees, head-of-line blocking, and processing delays.

### §5-1. Early-Response Gadgets

Early-response gadgets are enabling primitives that break the 0.CL deadlock by forcing the back-end to respond **before consuming the full request body**. They are critical for weaponizing otherwise-unexploitable desync conditions.

| Gadget Type | Mechanism | Example |
|-------------|-----------|---------|
| **OS-reserved filenames (IIS)** | Requesting `/con`, `/prn`, `/aux`, `/nul` triggers an OS-level exception → immediate 400/500 response | `GET /con HTTP/1.1` against IIS |
| **Static file serving** | Server responds to static file requests without waiting for POST body | `POST /favicon.ico HTTP/1.1` with body |
| **Server-level redirects** | 301/302 generated before body consumption | `POST /dir HTTP/1.1` → 301 to `/dir/` |
| **HEAD processing** | Some servers respond to HEAD without consuming body | `HEAD / HTTP/1.1` with Content-Length |
| **Expect: 100-continue** | Server sends 100 interim response, advancing pipeline state | `Expect: 100-continue` header |
| **Error responses** | Oversized URI/headers trigger immediate 414/431 errors | `GET /{'A'*65536} HTTP/1.1` |

**Pipeline advancement sequence:**
```
1. Attacker sends: Request_1 with hidden CL (front-end thinks no body)
2. Front-end immediately sends: Request_2 (attacker's next request)
3. Back-end: sees CL, waits for body...
4. Early-response gadget fires → back-end responds to Request_1 WITHOUT consuming body
5. Back-end reads: Request_2 bytes arrive → interpreted as body of Request_1
6. Pipeline DESYNC: Request_2's response is never generated;
   Request_3 (from another user) gets Request_2's "slot"
```

### §5-2. Pause-Based Desync

| Subtype | Mechanism | Key Condition |
|---------|-----------|---------------|
| **Server-timeout desync** | Send request headers promising a body → pause → server times out → but leaves connection open in its pool. Next request on this connection is prepended with leftover state | Server: `timeout > 0` AND doesn't close connection on timeout (Apache default: 60s, Varnish: 15s) |
| **Slow-body desync** | Send body bytes very slowly, one byte at a time. Intermediate proxies may time out and forward an incomplete request while the origin waits for more data | Different timeout values between proxy and origin |
| **Expect timeout race** | Send `Expect: 100-continue` but delay the body. Some proxies forward the next request before the origin sends its 100 Continue response | Proxy doesn't wait for 100 Continue before advancing pipeline |

### §5-3. Head-of-Line Blocking Exploitation

HTTP/1.1 pipelining suffers from response-side HOL blocking: the server must send responses in order, so a slow response blocks all subsequent responses.

| Subtype | Mechanism | Key Condition |
|---------|-----------|---------------|
| **Pipeline stalling** | Send a request to a slow endpoint as the first pipelined request. All subsequent responses are blocked until the slow response completes — can be used for timing attacks or to create predictable windows | Target has endpoints with variable response times |
| **Timeout amplification** | Pipeline many requests behind a slow one. When the slow request times out, the proxy may handle the remaining queued requests inconsistently — closing some, requeuing others | Proxy's timeout handling for queued pipeline requests |
| **Request ordering manipulation** | On proxies that reorder pipelined requests (violating RFC), an attacker can predict which response maps to which request slot, enabling targeted response capture | Proxy implementation reorders pipeline |

### §5-4. Pipeline Timing Oracles

| Subtype | Mechanism | Key Condition |
|---------|-----------|---------------|
| **Desync detection via timing** | Send a potentially smuggling payload and measure response time. If the front-end responds immediately but the back-end is "waiting" for body data, the response delay reveals the desync | Used by HTTP Request Smuggler's differential timing detection |
| **Connection-state inference** | Time the response to the first vs. second request on a connection. Different latencies reveal whether the server treats first requests specially | First-request routing detection |
| **Queue depth probing** | Send N pipelined requests and measure aggregate response time. Non-linear growth reveals server-side connection sharing or queuing behavior | Proxy connection pool analysis |

## §6. Pipeline-as-Amplifier (Impact Escalation)

A critical but underappreciated property: the pipeline **amplifies** the severity of otherwise low-impact vulnerabilities by converting them into cross-user attacks through the shared connection.

### §6-1. Low-Impact to Critical Escalation Paths

| Original Vulnerability | Severity Without Pipeline | Pipeline Amplification | Resulting Severity |
|-----------------------|--------------------------|----------------------|-------------------|
| **HTTP header injection (CRLF)** | Low — self-XSS or redirect | → Response queue poisoning (§1-3): injected CRLF splits the response, shifting the queue | **Critical** — mass session hijacking |
| **Open redirect** | Low — phishing | → Pipeline host switching: redirect on pipelined connection causes backend to follow redirect, mixing response streams | **High** — response leakage |
| **Reflected content in headers** | Info — header reflection | → Response desync: reflected content creates fake response boundaries | **Critical** — arbitrary response injection |
| **POST body ignored on static endpoint** | None — normal server behavior | → CL.0 client-side desync (§4-2): body poisons browser connection pool | **Critical** — cross-origin account takeover |
| **Server timeout on slow request** | None — normal server behavior | → Pause-based CSD (§5-2): timeout without connection close enables desync | **High** — client-side connection poisoning |

### §6-2. Infrastructure-Level Amplification

| Amplifier | Mechanism | Scale |
|-----------|-----------|-------|
| **CDN shared connection pools** | CDNs multiplex thousands of users onto a small pool of backend connections. One poisoned connection affects many users | Netlify: captured responses from **every site on the platform** |
| **Load balancer connection reuse** | LBs reuse backend connections across request batches. Pipeline poisoning persists across user sessions | Akamai Ghost request-smuggling class; do not conflate CVE-specific impact with Akamai program-wide 2025 bounty statistics |
| **Microservice mesh** | Internal service-to-service HTTP/1.1 connections share pipelines across unrelated API calls | One desync in service mesh poisons cross-service communication |

## §7. Protocol Transition Pipeline Attacks

Attacks at protocol boundaries where pipeline semantics change, appear, or disappear.

### §7-1. HTTP/2 → HTTP/1.1 Downgrade (Pipeline Reintroduction)

HTTP/2 uses binary framing with **no pipeline ambiguity** — each request is an independent stream. But when a front-end downgrades to HTTP/1.1 for backend communication, it **reintroduces the pipeline** with all its vulnerabilities.

| Subtype | Mechanism | Key Condition |
|---------|-----------|---------------|
| **H2.CL** | HTTP/2 front-end preserves Content-Length during downgrade. Back-end uses CL to frame the HTTP/1.1 pipeline message, disagreeing with the original HTTP/2 frame length | Front-end doesn't strip CL during translation |
| **H2.TE** | Front-end fails to remove Transfer-Encoding: chunked during downgrade (violating RFC 7540). Back-end processes chunked encoding on the pipeline | Front-end doesn't strip TE during downgrade |
| **H2.0** | HTTP/2 front-end drops body data during translation. Backend pipeline receives a bodyless request but CL/TE says otherwise | Lossy downgrade implementation |

The critical insight: HTTP/2 **clients** are protected from pipeline attacks, but the **backend pipeline** between the CDN and origin is HTTP/1.1 and fully vulnerable. The downgrade proxy bridges these worlds, and any translation error reintroduces pipeline-class attacks.

### §7-2. h2c Upgrade (Pipeline Escape)

| Subtype | Mechanism | Key Condition |
|---------|-----------|---------------|
| **h2c pipeline escape** | Client sends `Upgrade: h2c` on an HTTP/1.1 connection. Proxy forwards it as a normal HTTP/1.1 request. Backend upgrades to HTTP/2. Subsequent HTTP/2 binary frames are invisible to the HTTP/1.1 proxy — they bypass all proxy-level pipeline inspection | Proxy allows h2c Upgrade header; backend supports h2c |
| **Hidden h2c via connection tokens** | `Connection: Upgrade, HTTP2-Settings` header chain causes proxy to strip the Upgrade header, but the backend still processes the upgrade | Proxy implements Connection-token stripping but not upgrade prevention |

### §7-3. TLS / WebSocket Upgrade Pipeline Residue

| Subtype | Mechanism | Key Condition |
|---------|-----------|---------------|
| **TLS upgrade injection** | During HTTP → HTTPS transition (CONNECT tunnel or Upgrade), attacker injects data that persists in the pipeline across the protocol transition | Server processes pipelined data during handshake (CVE-2025-49812) |
| **WebSocket upgrade residue** | After `Upgrade: websocket`, unconsumed HTTP/1.1 body data persists in the connection. The WebSocket frame parser interprets it differently | Leftover HTTP bytes parsed as WebSocket frames |
| **Failed upgrade poisoning** | Upgrade request fails (4xx), but connection remains open. Request body intended for the upgraded protocol becomes a pipeline desync prefix | Server keeps connection alive after failed upgrade |

## §8. Pipeline Diagnostic Confusion

The boundary between legitimate HTTP pipelining and an actual smuggling vulnerability is notoriously blurry. Misdiagnosis in either direction is costly.

### §8-1. Pipelining vs. Smuggling — The False Positive Problem

| Diagnostic Signal | Pipelining (Benign) | Smuggling (Vulnerable) |
|-------------------|--------------------|-----------------------|
| **Two responses in one stream** | Normal — server processes both pipelined requests and returns two responses | Also normal for smuggling — not diagnostic |
| **Second request processed** | Server processes both requests because client sent them sequentially on keep-alive | Server processes a request the client didn't intend — injected via framing confusion |
| **Connection reuse** | Client explicitly sends second request | Second "request" is leftover bytes from a framing discrepancy |

The key distinction: **true smuggling creates a permanent disagreement** between two systems about request boundaries. Pipelining is two systems agreeing perfectly.

### §8-2. Diagnostic Techniques

| Technique | Method | What It Proves |
|-----------|--------|---------------|
| **Disable connection reuse** | Send only one request per connection. If the "smuggling" disappears, it was just pipelining | Rules out keep-alive false positives |
| **Timing-based early read** | After sending a chunked request (ending with `0\r\n\r\n`), pause and attempt to read. If server responds → front-end interpreted as chunked (vulnerable). If hang → front-end is still waiting for CL body (not vulnerable) | Differentiates TE vs. CL interpretation |
| **Connection-state probe** | HTTP Request Smuggler's automated probe: sends connection-state-dependent requests and compares responses | Detects first-request routing and connection-locked issues |
| **"Smuggling or pipelining?" action** | Burp Repeater custom action that applies the above diagnostics automatically | Quick triage in manual testing |

### §8-3. The False False-Positive

Sometimes what appears to be a pipelining false positive is actually a **real vulnerability**:

| Scenario | Why It Looks Like Pipelining | Why It's Actually Vulnerable |
|----------|----------------------------|-----------------------------|
| **CL.0 on same connection** | Server processes both requests — looks like normal keep-alive | Server ignored Content-Length, treating body as next request — CL.0 desync |
| **Connection-state desync** | First request works, second request works — seems fine | Second request bypasses access controls because proxy cached auth from first request |
| **Client-side only** | No proxy involved, so traditional CL.TE detection doesn't trigger | Browser-to-server CL.0 creates client-side desync exploitable via JavaScript |

## Summary: Core Principles

### Why the Pipeline Is Fundamentally Vulnerable

The HTTP/1.1 pipeline multiplexes logically independent transactions onto a single ordered byte stream with no structural delimiter between sessions. The FIFO contract, request isolation contract, and connection integrity contract are all **implicit** — enforced only by correct implementation, never by the protocol structure itself. Any discrepancy between two processors about message boundaries destroys all three contracts simultaneously.

### Why Pipeline Attacks Keep Evolving

1. **New injection primitives** expand what can be done post-injection. 0.CL was considered dead until early-response gadgets revived it. Expect headers were ignored for decades. Chunk extensions bypassed all existing CL/TE-focused defenses.
2. **Infrastructure amplifies everything**. CDNs sharing backend connections across millions of users transform a single-connection desync into platform-wide response leakage.
3. **Client-side opened a new front**. CSD attacks proved that the pipeline vulnerability exists not just between proxy and origin, but between browser and server — no proxy required.
4. **Low-impact bugs become critical**. The pipeline's cross-user nature means that a header injection, an open redirect, or even a server timeout behavior becomes a vector for mass session hijacking.

### The Structural Solution

**Eliminate the pipeline.** HTTP/2's binary framing removes the ambiguous shared byte stream — each request is an independent, clearly-delimited stream with no ordering dependency. The only viable long-term fix is **end-to-end HTTP/2**, including upstream connections between CDN/proxy and origin. As of 2025, nginx, Akamai, CloudFront, and Fastly still lack full upstream HTTP/2 support, keeping the HTTP/1.1 pipeline — and its entire attack surface — alive.

## Appendix A: Pipeline Injection Primitives (HRS Summary)

These are the HTTP Request Smuggling techniques used to **inject extra requests** into a pipeline. They are the prerequisite for most attacks in §1–§7 but are not themselves pipeline-specific attacks. For comprehensive HRS taxonomy, see dedicated HRS resources.

| Primitive | Mechanism | One-Line Summary |
|-----------|-----------|-----------------|
| **CL.TE** | Front-end uses Content-Length, back-end uses Transfer-Encoding | Classic: body excess after CL boundary becomes next pipeline request |
| **TE.CL** | Front-end uses Transfer-Encoding, back-end uses Content-Length | Classic: early chunk termination leaves body remainder as next request |
| **TE.TE** | Both use TE, but obfuscated TE causes one to fall back to CL | TE header obfuscation (whitespace, case, value mutation, obs-fold) |
| **CL.0** | Front-end uses CL, back-end ignores body entirely | Body of POST to static endpoint becomes next pipeline request |
| **0.CL** | Front-end sees no CL (hidden), back-end sees CL | Requires early-response gadget to break deadlock |
| **TE.0** | Front-end dechunks, back-end ignores TE entirely | Chunked body + smuggled request forwarded raw |
| **H2.CL** | HTTP/2 front-end preserves CL during downgrade to HTTP/1.1 | CL disagrees with HTTP/2 frame length on backend pipeline |
| **H2.TE** | HTTP/2 front-end preserves TE during downgrade | TE header shouldn't exist in HTTP/2-originated request |
| **Chunk extension** | Ambiguous line terminators in chunk extensions | "Funky chunks" — `\n` / `\r` parsing differences |
